# 4JURIS Pessoas · Módulos v2

Recrutamento (vagas + ATS + portal de carreiras), Central de pesquisas, Arquitetura de cargos,
Organograma e People Analytics. Este documento é o **contrato** entre os módulos e o registro
das decisões de arquitetura.

## 1. Auditoria resumida do sistema existente

| Item | Achado |
|---|---|
| Stack | Vite 7 + React 18 + TS strict + React Router 6 + Tailwind 3 + Zustand 4. Funções serverless em `api/` (Vercel), PostgreSQL (Supabase) via `pg`. Testes: Vitest. |
| Persistência legada | Cada coleção do app é uma tabela JSONB (`app_<coleção>`), reescrita **por inteiro** por `PUT /api/estado` a partir da store do cliente. |
| Autenticação | `POST /api/login` (scrypt), cookie `sessao4juris` HttpOnly assinado com HMAC. Papéis em `colaboradores[].papel`: `colaborador, gestor, rh, diretoria, admin`. |
| Autorização legada | Matriz em `src/domain/permissions.ts`, usada só na interface. **O servidor não verificava nada** (ver riscos). |
| O que é real | Tudo que a store grava no banco (pessoas, áreas, funções, contratos, NFs…). Em modo `demo` os dados ficam no `localStorage`. |
| Pesquisas existentes | Pesquisas anônimas simples (`pesquisas/respostas/participacoes` JSONB), com supressão por grupo pequeno. Mantidas. |
| Engenharia de funções | `Cargo` (JSONB) já tem CBO, atividades, habilidades, faixa de valor, perfil ideal. **É a fonte da verdade do cargo**; a v2 só acrescenta o que falta. |
| Organização | `Colaborador.responsavelId` (gestor imediato), `setorId`, `cargoId`, `unidadeId`; `Setor.gestorId/liderancaIds`. |

### Riscos encontrados (e o que foi feito)

1. **Escrita irrestrita em `/api/estado`** – qualquer pessoa logada podia se tornar admin ou reescrever áreas/contratos/auditoria. **Corrigido**: `api/_v2/guarda.ts` valida no servidor (papéis só pela administração; estrutura, contratos e configurações só RH/admin; auditoria só acrescenta).
2. **`GET /api/estado` entregava todo o estado a qualquer pessoa logada** (contratos, CPF, dados bancários). **Corrigido**: a leitura é filtrada por permissão no servidor (`filtrarEstado` em `api/_v2/guarda.ts`) e a gravação é por registro, com mescla dos campos que a pessoa não vê (`api/_v2/estadoLegado.ts`). Coberto por `api/estado.test.ts`. Os módulos v2 continuam **nunca** devolvendo dados por esse caminho.
3. Anonimato das pesquisas legadas é "de interface" (documentado em `docs/ARQUITETURA.md`). A Central de pesquisas v2 resolve com desenho de dados (ver §5).

## 2. Arquitetura dos módulos v2

```
db/v2/NN-*.sql            migrações aditivas e idempotentes (aplicadas por `npm run db:setup`)
api/v2/index.ts           função serverless única → despacha para api/_v2
api/_v2/nucleo.ts         tipos, erros, roteador, auth, helpers (validação, auditoria, notificação, org)
api/_v2/arquivos.ts       upload/download seguro (bytea, validação por magic bytes, 3 MB)
api/_v2/guarda.ts         guarda do /api/estado legado
api/_v2/modulos/*.ts      um arquivo por módulo; cada um exporta `rotas: Rota[]`
api/_v2/teste/harness.ts  banco PGlite em memória + sessão + `chamar()` para testes ponta a ponta
src/domain/v2/*           regras PURAS (sem React/DB; só imports relativos) – usadas pelo servidor e pelo cliente
src/data/v2/api.ts        cliente HTTP (`api`, `useApi`, `executar`, `lerBase64`, `qs`)
src/data/v2/acesso.ts     capacidades da sessão (`useTem`)
src/components/v2/*       componentes compartilhados (estados, Drawer, Paginacao, Stepper, StatusBadge, charts2)
src/pages/v2/<modulo>/*   telas
```

### Regras de ouro

* **Servidor decide.** Toda rota autenticada declara `cap`; o roteador recusa (403) sem a capacidade. Escopo por registro (ex.: gestor só vê vagas da própria área) é feito na consulta SQL do módulo, nunca no cliente.
* **Capacidades** = papel + funções adicionais (`acl_funcoes`: `recrutador`, `analista_rh`, `resp_pesquisas`, `aprovador_financeiro`). Fonte única: `src/domain/permissions.ts` (`capacidadesDe`). Novas capacidades já existem: `vagas:*`, `ats:*`, `pesq:*`, `cargos:*`, `org:*`, `analytics:ver`.
* **Fonte da verdade da organização**: `app_colaboradores`, `app_setores`, `app_cargos`, `app_unidades` (JSONB legado). Tabelas v2 guardam apenas os IDs (texto) e validam no servidor com `pessoaPorId/pessoas/setores/cargos/unidades` de `nucleo.ts`. **A API v2 nunca escreve nessas coleções** (a store do cliente reescreve coleções inteiras e apagaria a alteração). Edições de pessoas/áreas/funções continuam pelas ações da store (que o `guarda.ts` protege).
* **Rotas públicas** (`publica: true`) não leem cookie, têm limite por IP (tabela `lim_tentativas`) e só devolvem campos próprios para o público.
* **CSRF**: mutações autenticadas exigem `X-Requested-With: 4juris` (o cliente `api` já envia).
* **Auditoria** (`auditar`) em toda ação crítica; **notificação** (`notificar`) com `chave` para não duplicar; nunca colocar dado sensível em título/corpo.
* **Sem simulação**: envio de e-mail só é "enviado" se o Resend respondeu OK; sem `RESEND_API_KEY` o status é `nao_configurado`. Mensagem de sucesso na interface só depois da confirmação do servidor (`executar`).
* **Erros**: `throw invalido()/proibido()/naoEncontrado()/conflito()`; mensagens em pt-BR; campos inválidos em `campos`.
* **Paginação** em toda listagem (`paginacao()`); respostas `{ itens, total, pagina, por }`.

### Contrato de dados sensíveis

| Dado | Quem vê |
|---|---|
| Faixa salarial da vaga, proposta | `vagas:ver_remuneracao` (RH, recrutador atribuído à vaga via `vagas:gerenciar`, aprovador financeiro). Gestor **não**. |
| Observações do RH, notas `visibilidade='rh'` | `ats:notas_rh` |
| Notas `banca`, avaliações | RH/recrutador; gestor/entrevistador só nas candidaturas das suas vagas/entrevistas |
| Currículo e documentos | quem tem `ats:ver` no escopo da vaga; download sempre por rota autenticada |
| Respostas de pesquisa anônima | ninguém individualmente; agregados com mínimo de grupo e supressão complementar |
| Faixas salariais de cargos | `cargos:ver_faixas` |

## 3. Recrutamento (vagas + ATS + portal)

Tabelas: `rec_*` (ver `db/v2/10-vagas.sql`, `20-ats.sql`).

* Ciclo da vaga: `rascunho → em_aprovacao → (ajustes ↔ em_aprovacao) → aprovada → publicada ⇄ pausada → encerrada`; `cancelada` a partir de qualquer estado não final. **Publicar exige `aprovada`** (ou fluxo sem aprovações). Fluxos configuráveis em `rec_config('fluxos_aprovacao')`.
* Uma candidatura pertence a um **candidato reutilizável** e a **uma vaga** (`unique(vaga_id, candidato_id)`); duplicidade é tratada no envio.
* Portal público: só vagas `publicada` e dentro de `encerra_candidaturas_em`; campos internos nunca saem.
* Pipeline: etapas por vaga (`rec_vaga_etapas`); movimentações em `rec_candidatura_movs` (base dos tempos por etapa e do tempo de preenchimento).
* Definições de indicadores: ver `src/domain/v2/indicadoresRecrutamento.ts`.

### 3.1 Divulgação, modelos e PDF da vaga

* **Campos de divulgação** (`92-rh-vagas-pesquisas.sql`): `desafios`, `jornada` e `etapas_processo` (lista exibida ao candidato). As etapas do pipeline (`rec_vaga_etapas`) continuam internas.
* **Modelos de vaga** (`src/domain/v2/vagaModelos.ts`): SDR, Closer, Gestor de tráfego, Designer, Desenvolvedor, Customer Success, Analista administrativo e Analista de RH. Preenchem só a descrição da função (oportunidade, responsabilidades, desafios, requisitos); remuneração, vantagens e jornada nunca vêm do modelo. Vagas anteriores são reaproveitadas com **Duplicar**.
* **Formulário**: campos essenciais à vista; "Mais detalhes" (opcional) com área, posições, senioridade, desafios, diferenciais, jornada, etapas, datas e faixa salarial (só com `vagas:ver_remuneracao`).
* **Divulgação**: a página da vaga mostra o link com Copiar, WhatsApp, Abrir página e PDF. Fora do ar, explica por que o link não funciona.
* **PDF** (`src/components/v2/vagas/DocumentoVaga.tsx`): um template A4 alimentado pela vaga, gerado pelo diálogo de impressão do navegador ("Salvar como PDF"), sem biblioteca nova. Seções vazias são omitidas; a prévia administrativa lista o que não foi informado. Vaga não publicada sai com o aviso "Documento interno"; a faixa salarial só aparece se a vaga marcou *divulgar*. Também disponível na página pública. Traz QR Code do link de candidatura no cabeçalho (`qrcode-generator`, SVG; só em vaga publicada) e o link por extenso.
* **Visualizações e conversão** (`93-vagas-visualizacoes.sql`): cada abertura da página pública soma 1 em `rec_vagas.visualizacoes` (contador agregado, sem IP nem cookie; não altera a `versao`). A barra de divulgação mostra visualizações, candidaturas e conversão (candidaturas ÷ visualizações). Número aproximado: inclui acessos internos e robôs.

## 4. Engenharia de cargos

`cargo_id` das tabelas `cg_*` = `Cargo.id` legado. A v2 adiciona famílias/subfamílias, trilhas, níveis, ficha oficial versionada, matriz de competências (usa `Competencia.id` legada), faixas salariais com vigência/aprovação e governança. Cargo inativo permanece referenciável por vagas/posições antigas.

## 5. Central de pesquisas

* Estrutura publicada é **imutável por versão** (`pq_versoes.perguntas` = retrato); cada resposta guarda a versão.
* **Anônima**: `pq_respostas` **não** tem `colaborador_id`, `convite_id` nem hora (só data); o convite guarda `usado_em` apenas como data. Segmentos (área/unidade) só são exibidos se o grupo atingir o mínimo, com supressão complementar para impedir subtração.
* **Identificada**: guarda `colaborador_id` e a tela informa quem acessa e para quê; nunca é rotulada como anônima.
* Convites individuais com token (hash no banco, validade, uso único); links públicos com regras próprias (sem prometer anonimato incompatível).

### 5.1 Destaques e plano de ação

* **Destaques por dimensão** (`destaquesDimensoes`): média ≥ 4,0 é ponto forte; < 3,5 merece investigação (escala 1–5, só dimensões com respostas ≥ mínimo do grupo). A tela separa o observado da hipótese.
* **Plano de ação** (`pq_acoes`): problema observado, ação, dimensão, responsável, prazo, status (`planejada → em_andamento → concluida | cancelada`), indicador de acompanhamento e registro de conclusão. Leitura com `pesq:gerenciar` ou `pesq:resultados`; escrita só com `pesq:gerenciar`. O responsável é notificado; ações atrasadas aparecem no painel. Nenhuma resposta individual é copiada para o plano.
* **Modelos novos**: comunicação e integração entre áreas, segurança psicológica, onboarding de 7, 30 e 60–90 dias.
* **Seções na resposta**: `PerguntaPesquisa.secao`. Perguntas seguidas com a mesma seção aparecem juntas numa página (`paginasDeResposta`); sem seção, uma por página (comportamento anterior). A seção não entra na assinatura de comparação entre versões. Modelos curtos (pulso, onboarding 7 dias) já vêm numa página só.

## 6. Organograma e People Analytics

Gerados dos relacionamentos explícitos (`responsavelId`, `setorId`, `cargoId`). Nunca se deduz subordinação por nome/senioridade; lacunas viram pendências. Edição de hierarquia usa as ações da store (que persistem e auditam) com validação de ciclos (`src/domain/v2/organograma.ts`). Indicadores indisponíveis (rotatividade de folha, absenteísmo…) aparecem como "indisponível – depende de…".

## 7. Como adicionar uma rota

```ts
// api/_v2/modulos/exemplo.ts
export const rotas: Rota[] = [
  { metodo: 'GET', padrao: 'vagas/:id', cap: 'vagas:ver', h: async ({ db, params, usuario }) => ok({ ... }) },
]
```
Registrada em `api/_v2/rotas.ts`. Teste com `chamar()` do harness (`api/_v2/*.test.ts`).

## 8. Variáveis de ambiente (servidor)

`DATABASE_URL`, `SESSION_SECRET` (já usadas). Opcionais: `RESEND_API_KEY`, `RESEND_FROM`, `PORTAL_URL` (e-mails reais). Sem `RESEND_API_KEY`, comunicações ficam `nao_configurado`.
